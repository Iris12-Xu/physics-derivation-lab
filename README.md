# Physics Derivation Lab

> 面向物理仿真与科研编程的可检查公式推导、验证与代码生成系统。

> **项目状态：设计已确认，尚未进入功能实现。**
> 本 README 面向开发团队，记录当前有效的项目定位、核心原则、MVP 边界和验收标准。文中标为“计划”的能力不代表已经可用。

> **核心目标：** 把一次性的物理推导，转换为可执行、可审查、可维护、可复现的工程资产。

## 项目是什么

Physics Derivation Lab 试图解决基础物理规律与可运行数值代码之间的工程断层。

用户可能记得斯涅耳定律、牛顿定律或麦克斯韦方程，却仍然需要完成模型选择、变量定义、几何关系补全、符号推导、数学分支筛选、适用条件检查、数值稳定性处理和代码实现。任何一个环节出错，都可能得到数学上可计算、物理上却不成立的结果。

本项目把这条过程视为一种受约束的“编译”：

```text
结构化物理问题
    ↓
带物理语义的模型
    ↓
审核过的定律与关系
    ↓
可追踪的符号推导
    ↓
物理解筛选与验证
    ↓
可运行、可测试的数值代码
```

“物理公式编译器”是架构隐喻，不表示系统能够从任意一句自然语言或任意一条基础定律自动推出所有公式。

## 为什么需要这个项目

简单查公式、完成一次性作业或快速获得近似答案时，教材、通用 AI 和 SymPy 通常已经足够。本项目不试图替代这些工具。

Physics Derivation Lab 面向另一类问题：物理公式将进入需要长期维护、多人协作、反复修改或接受审核的仿真与科研代码。此时，一段看起来正确的推导或一份能够运行的代码还不够，团队还需要知道：

- 当前代码实现了哪个物理模型；
- 使用了哪些定律、约定和近似；
- 推导过程是否可以重放；
- 数学分支为什么被保留或拒绝；
- 公式是否经过独立正确性验证；
- 模型或代码修改后，哪些结论需要重新检查。

项目最终交付的不是一个孤立公式，而是一份可以版本化的推导资产：

```text
物理模型与假设
    +
基础定律及来源
    +
完整推导轨迹
    +
候选解与筛选理由
    +
独立验证证据
    +
可运行代码与自动测试
```

因此，项目的核心问题不是“这个公式怎么算”，而是：

> 我们怎样证明一段长期运行的科研代码，确实实现了所声明的物理模型？

### 什么时候不需要本项目

- 只想查询一个已知公式；
- 只需要一次性的手工计算；
- 结果不进入长期维护的代码或研究记录；
- 不需要保存来源、条件、推导过程和验证证据。

## 首要用户

第一阶段服务于：

- 物理仿真开发者；
- 科研编程人员；
- 负责维护物理模型、数值算法和验证用例的开发团队。

推导过程会保留物理解释，因此未来也可以支持教学场景，但教学不是 MVP 的主要验收目标。

## 要解决的问题

- 基础定律已知，但目标公式的推导链不完整；
- 坐标系、参考方向、角度和正负号容易混淆；
- 输入条件不足或互相矛盾时，现有工具常常不能清楚解释缺口；
- 符号工具可能返回多个数学解，却不负责判断物理可行性；
- 数学等价表达式在数值稳定性、精度和执行成本上可能不同；
- 推导结果还需要人工翻译为 NumPy、C++ 或 CUDA 代码；
- AI 能给出建议，但不能天然证明公式、模型或适用条件正确；
- 普通公式库适合查询已有结果，不擅长组合基础关系形成可审查的新推导。

项目的目标不是“查到一个公式”，而是形成从结构化问题到可验证数值算法的完整证据链。

## 已确定的核心原则

以下原则是当前架构与实现必须遵守的约束。

### 1. 确定性核心不依赖 AI

YAML、JSON 或 Python API 等结构化输入必须能够直接驱动核心流程。AI 未来可以负责自然语言理解、缺失条件提问和结果解释，但不能成为推导执行或正确性判断的唯一来源。

AI 不在核心系统的必经依赖链上：

- **核心路径**：用户通过 YAML、JSON、Python API 或表单直接提交结构化问题；
- **可选前端**：AI 把自然语言转换为待确认的 Physics IR；
- **可选审核输入**：人或 AI 提交候选推导，由系统重建、检查和验证。

没有 AI 时，推导、结果呈现、验证、代码生成和测试流程仍然必须完整运行。MVP 只实现核心路径；AI 前端和候选推导审核属于后续能力。

### 2. 物理知识必须可追溯

进入可靠知识库的定律、几何关系和推导模板必须记录：

- 来源；
- 变量定义；
- 适用条件；
- 模型假设；
- 审核状态。

AI 或用户临时提交的表达式不能自动升级为可靠知识。

### 3. 推导必须可重放

每一步推导都要保存输入、操作、输出和验证结果。开发者应能定位错误发生在模型、知识关系、符号操作、分支选择还是代码生成阶段。

### 4. 数学解不等于物理解

符号引擎产生的候选解必须继续接受定义域、变量范围、传播方向、模型条件和原方程代回检查。系统应说明每个候选解为什么被保留或拒绝。

### 5. 验证结论必须分级

系统不能用一个模糊的“验证通过”覆盖不同性质的结论。至少要区分：

- 程序能够自动验证的数学或数值条件；
- 由模型预设但无法在当前任务中证明的假设；
- 由用户确认的外部条件；
- 未验证或验证失败的部分。

验证还必须区分两个层次：

- **内部一致性验证**：候选解能否代回原方程、变换前后是否等价、生成代码是否忠实实现符号表达式；
- **独立正确性验证**：公式是否符合独立人工解析结果、教材或论文参考值、不同计算路径、守恒律、极限行为或可信外部模拟。

内部一致性不能代替独立正确性。错误公式及其忠实生成的错误代码可能共同通过内部对照测试。

### 6. 知识不足时明确停止

缺少控制方程、几何关系、边界条件、变量定义或适用条件时，系统应报告推导链断点和所需信息，不得凭空补全公式。

## 处理模型

项目采用分层中间表示，但当前只固定各层职责，不冻结具体类、字段或序列化格式。

```text
结构化输入 ──────────────────────────────┐
自然语言 ── 后续可选 AI 转换并由用户确认 ─┼─→ Physics IR
候选推导 ── 后续可选审核导入 ────────────┘
                                             ↓
                                        Symbolic IR
                                             ↓
                           推导步骤、候选解与最终结果呈现
                                             ↓
                                  约束检查与独立正确性验证
                                             ↓
                                        Numerical IR
                                             ↓
                              NumPy / C++ / CUDA / 其他后端
```

- **Physics IR**：保存物理量、模型、定律、单位、约束、适用条件和解的物理语义；
- **Symbolic IR**：保存方程、表达式、候选解和可验证的推导步骤；
- **Numerical IR**：保存面向实际计算的表达式图、分支和公共子表达式；
- **代码后端**：生成目标平台可以运行和测试的实现。

MVP 需要建立最小 Physics IR 和符号推导闭环；完整 Numerical IR 属于后续里程碑。

## 架构摘要

系统计划由以下职责组成：

1. **输入与校验**：读取结构化任务，检查目标、变量、单位、模型和约束；
2. **物理知识库**：提供经过审核的物理定律、几何关系和推导模板；
3. **推导规划**：从目标反向建立依赖，选择确定性的推导步骤；
4. **符号执行**：使用 SymPy 执行求解、代入、消元、求导和化简；
5. **约束与验证**：筛选分支，执行代回、量纲、范围、极限和数值交叉检查；
6. **代码生成**：把已验证表达式转换为 NumPy 等目标后端，并生成对照测试。

这些是职责边界，不是已经冻结的包结构。详细设计见 [架构说明](docs/architecture.md)。

## MVP：斯涅耳定律完整闭环

MVP 只证明一件事：系统能够可靠地把一个受支持的斯涅耳定律任务转换为经过筛选和验证的 NumPy 实现。

### 输入示例

```yaml
problem: refraction_angle

known:
  n1: 1.0
  n2: 1.333
  theta_i:
    value: 30
    unit: degree

target:
  - theta_t

model:
  approximation: geometric_optics
  interface: locally_smooth

output:
  backend: numpy
  precision: float64
```

### MVP 固定流程

```text
YAML 结构化输入
    ↓
Physics IR 校验
    ↓
审核知识关系检索
    ↓
确定性推导计划
    ↓
SymPy 执行
    ↓
数学分支分类与物理解筛选
    ↓
验证报告
    ↓
NumPy 代码与 pytest
```

### MVP 验收标准

- [ ] 能读取并校验受支持的斯涅耳定律 YAML 任务；
- [ ] 能明确区分已知量、未知量、单位、范围、模型和目标；
- [ ] 能从审核知识中取得
  \(n_1\sin\theta_i=n_2\sin\theta_t\) 及其适用条件；
- [ ] 能生成并执行确定性推导步骤；
- [ ] 能识别正常折射、无可传播实数解和全反射相关条件；
- [ ] 能列出候选数学解，并说明保留或拒绝原因；
- [ ] 能执行原方程代回、量纲、范围和随机数值交叉检查；
- [ ] 能使用至少一组独立于主推导路径的可信参考结果验证最终公式；
- [ ] 能生成可运行的 NumPy 代码；
- [ ] 能用 pytest 对照符号结果与生成代码；
- [ ] 对缺失、矛盾或不受支持的输入返回明确状态，不伪造结果。

建议的任务状态包括：

```text
READY_TO_DERIVE
NEEDS_INFORMATION
INCONSISTENT
NEEDS_BRANCH_SELECTION
NUMERICAL_ONLY
UNSUPPORTED
```

具体命名仍可在实现中调整，但错误必须可区分、可解释。

### 暂不纳入 MVP

以下能力不是放弃，而是在 MVP 闭环稳定后继续实现：

- AI 自然语言输入；
- Web 可视化界面；
- C++ 和 CUDA 后端；
- 彩虹驻点角综合案例；
- 完整 Numerical IR 与性能优化；
- Level C 通用动态推导；
- 几何光学之外的物理领域。

## MVP 后的第一个综合案例

斯涅耳定律闭环通过后，项目将以球形水滴的彩虹驻点角作为第一个综合案例，用于检验：

- 多条物理与几何关系的组合；
- 角度约定和传播方向；
- 多次数内部反射；
- 偏向角与驻点条件；
- 多个数学分支；
- 折射率色散；
- 符号结果与数值求根的交叉验证；
- 与外部可信数据或 Opticks 结果的对照。

彩虹案例是架构验证的重要阶段，但不阻塞 MVP 完成。

- Python 3.11+；
- Pydantic；
- SymPy；
- NumPy；
- PyYAML；
- pytest。
