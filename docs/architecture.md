# 架构说明

> 状态：设计草案。本文细化 README 中已经确定的架构职责，但不冻结包结构和内部 API。

## 1. 架构目标

Physics Derivation Lab 的核心不是让符号引擎“猜公式”，而是建立一条带有物理语义和验证证据的确定性处理链。

架构必须支持：

- 结构化描述问题；
- 追踪每个关系的来源和适用条件；
- 规划并执行可重放的推导步骤；
- 保留全部候选数学解；
- 根据物理约束筛选候选解；
- 报告验证覆盖范围和未验证假设；
- 从同一已验证表达式生成代码和测试。

## 2. 分层中间表示

```text
Input
  │
  ▼
Physics IR ──物理语义、模型、知识来源、约束
  │
  ▼
Symbolic IR ─方程、表达式、推导步骤、候选解
  │
  ▼
Numerical IR ─数值表达式图、分支、稳定性和优化信息
  │
  ▼
Backend ─────NumPy / Python / C++ / CUDA
```

### Physics IR

回答：

- 当前研究的对象是什么；
- 每个物理量是什么；
- 使用哪些定律和模型；
- 哪些条件可自动检查；
- 哪些内容只是声明性假设；
- 解必须满足什么物理条件。

### Symbolic IR

回答：

- 当前有哪些方程和表达式；
- 执行了哪些符号操作；
- 每一步的输入和输出是什么；
- 符号引擎生成了哪些候选解；
- 哪些验证与某一步相关。

### Numerical IR

回答：

- 如何安全地数值求值；
- 哪些分支必须显式处理；
- 哪些公共子表达式可以复用；
- 对参数范围和精度有什么要求；
- 哪些等价形式在目标平台上更稳定。

MVP 不要求完整 Numerical IR。第一版可以由已验证的符号表达式直接生成受限的 NumPy 代码，但接口不得阻碍后续引入 Numerical IR。

## 3. 核心职责

### 3.1 输入与校验

负责：

- 解析 YAML 或 JSON；
- 校验任务结构；
- 识别已知量、未知量和目标；
- 规范化单位与角度表示；
- 检查必要模型和输出选项；
- 构造 Physics IR。

不负责：

- 猜测缺失的物理关系；
- 将任意输入文本作为代码执行；
- 替用户默默选择重要模型假设。

### 3.2 物理知识库

知识条目包括：

- 物理量定义；
- 基础定律；
- 几何关系；
- 模型；
- 推导模板；
- 数据来源；
- 审核状态。

知识库不需要预存所有最终公式，但必须包含完成受支持推导所需的基础关系。

### 3.3 推导规划

规划器从目标反向分析依赖。

允许的操作应使用白名单，例如：

```text
solve
substitute
eliminate
differentiate
integrate
simplify
expand
factor
take_limit
select_branch
```

MVP 优先执行审核模板或固定计划，不要求通用搜索算法。

### 3.4 符号执行

第一版计划使用 SymPy 执行：

- 方程求解；
- 代入和消元；
- 求导；
- 三角表达式处理；
- 候选分支生成；
- LaTeX 和代码表达式输出。

符号执行器只执行已经进入中间表示的表达式和操作，不负责决定物理定律。

### 3.5 约束与验证

验证应拆分为独立项目：

| 验证项 | 示例 |
| --- | --- |
| 结构检查 | 目标、变量、模型是否存在 |
| 类型检查 | 标量、向量、张量是否匹配 |
| 单位与量纲 | 方程两侧量纲是否一致 |
| 定义域与范围 | 角度、折射率、根号和反三角函数输入 |
| 原方程代回 | 候选解是否满足输入方程 |
| 符号等价 | 变换前后是否等价 |
| 数值交叉检查 | 随机采样或独立数值计算 |
| 极限与边界 | 法向入射、临界角附近等 |
| 独立正确性 | 人工解析、可信参考值、不同计算路径或外部模拟 |
| 生成代码差分 | 后端实现是否匹配符号表达式 |
| 模型条件 | 是否仅为用户声明或预设 |

验证证据分成两组：

- **内部一致性证据**：原方程代回、符号等价、生成代码差分；
- **独立正确性证据**：不复用主推导结论的参考答案、计算路径、物理不变量、极限结果或外部模拟。

内部一致性只能证明系统各阶段彼此一致，不能单独证明起始定律、模型或最终公式正确。对 MVP 支持的标准案例，最终报告必须至少包含一项独立正确性证据。

建议的验证级别：

```text
VERIFIED
PARTIALLY_VERIFIED
USER_CONFIRMED
UNVERIFIED
FAILED
```

### 3.6 代码生成

代码生成必须消费已经通过相应验证的表达式，并同时生成：

- 目标语言代码；
- 参数与范围说明；
- 必要分支判断；
- 与符号结果对照的测试；
- 未验证假设和适用条件。

MVP 只实现 NumPy `float64` 路径。

## 4. 推导策略

系统长期采用四级策略：

| 级别 | 含义 | MVP |
| --- | --- | --- |
| Level A | 审核推导模板 | 支持 |
| Level B | 多个审核模板或关系组合 | MVP 后 |
| Level C | 受约束的动态推导规划 | MVP 后 |
| Level D | 知识不足，明确停止 | 支持 |

Level D 是可靠行为，不是异常兜底。系统必须能说明缺少哪个变量、关系、条件或能力。

## 5. 数学分支处理

候选解的基本处理顺序：

```text
符号候选解
    ↓
实数域与函数定义域检查
    ↓
变量范围检查
    ↓
原方程代回
    ↓
模型与传播方向检查
    ↓
数值交叉验证
    ↓
推荐 / 物理可能 / 拒绝
```

拒绝结果时必须记录原因。用户未来可以研究被拒绝分支，但界面和 API 必须保留“未通过当前物理约束”的标记。

## 6. AI 边界

AI 是可选前端，只能通过核心系统暴露的受控接口工作。

允许的职责：

- 把自然语言映射为待确认的 Physics IR；
- 识别描述中的缺失项；
- 每次提出一个高价值澄清问题；
- 推荐知识库中已有的定律或模型；
- 解释推导、验证和失败报告。

禁止绕过的边界：

- AI 输出不能直接成为已审核定律；
- AI 不能跳过适用条件和分支筛选；
- AI 不能把语言自信度当成验证证据；
- 核心系统不能反向依赖 AI 才能运行。

## 7. 安全边界

- 不使用 `eval` 执行用户或 AI 提交的表达式；
- 只允许白名单符号、常量、函数和操作；
- 知识条目与任务输入使用独立信任级别；
- 代码生成结果在隔离环境或受控测试中验证；
- 错误信息不得掩盖缺失知识或不支持能力。

## 8. 可调整的实现结构

初始实现可能按以下职责组织，但目录与包名不是合同：

```text
src/pdl/
├── ir/
├── knowledge/
├── planner/
├── executor/
├── verifier/
├── codegen/
└── api/
```

只有在 MVP 测试暴露真实边界后，才决定是否需要独立的 `optimizer/`、`numerical_ir/` 或 `ai/` 包。
